# 📚 Сервис учёта домашней библиотеки

REST API сервис для управления коллекцией бумажных книг с поддержкой многопоточной обработки, кэширования и блокировок.

## 🎯 О проекте

Приложение для владельцев бумажных книг, помогающее вести учёт коллекции, отслеживать местоположение книг, 
не покупать двойные экземпляры и сохранять впечатления от прочитанного.

### Ключевые возможности:
- **CRUD операции** с книгами и авторами через REST API
- **Пакетное добавление книг** с автоматическим созданием отсутствующих авторов
- **Кэширование авторов** для уменьшения нагрузки на базу данных
- **Поддержка многопоточности** с защитой от конкурентных конфликтов
- **Оптимизация запросов** к базе данных (решение проблемы N+1)
- **Интеграционное тестирование** с реальными сервисами в Docker-контейнерах

## 🧠 Ключевые процессы

### 📖 CRUD операции с книгами и авторами

**REST API** предоставляет стандартные операции для управления коллекцией:

- `POST /v1/books/authors` — добавление автора
- `POST /v1/books` — пакетное добавление книг (с автоматическим созданием отсутствующих авторов)
- `GET /v1/books/{bookId}` — получение книги по ID
- `PATCH /v1/books/{bookId}` — частичное обновление информации о книге
- `DELETE /v1/books/{bookId}` — удаление книги
- `GET /v1/books/filter` — поиск и фильтрация книг по автору и названию через query-параметры

### 📦 Пакетное добавление книг

**Главный метод:** `addBookList(List<BookDto> books)` — принимает список книг и обрабатывает их группами по авторам.

**Вспомогательные операции:**
-  **Группировка по авторам** — книги группируются для минимизации запросов к БД
-  **Кэширование** — проверка наличия автора в кэше перед запросом к БД
-  **Создание авторов** — автоматическое создание отсутствующих авторов
-  **Сохранение книг** — массовое сохранение книг с привязкой к авторам

**Оптимизация:** кэширование через `@CachePut` уменьшило количество запросов к БД при пакетных операциях.

### 🔒 Многопоточность и блокировки

**Проблема:** при параллельном добавлении книг одному автору возможны конфликты.

**Решение:**
- Optimistic locking (`@Version`) — проверка версии при обновлении, её не хватило
- Pessimistic locking (`@Lock(LockModeType.PESSIMISTIC_WRITE)`) — блокировка строки на уровне БД

**Тестирование:** тесты с `CompletableFuture` проверяют корректную работу метода при параллельных вызовах из нескольких потоков.

### ⚡ Оптимизация запросов к БД

**Проблема:** N+1 — при загрузке  автора с 3 книгами выполнялось 4 запросов (1 для авторов + 3 для книг каждого автора).

**Решение:**
- @EntityGraph — указание связанных сущностей для загрузки в одном запросе
- LEFT JOIN FETCH — явное указание JOIN для eager loading

**Результат:** 1 запрос вместо 4.

## Интеграционные тесты с Testcontainers

### PostgreSQL 17:
- Репозитории (сохранение, поиск, обновление)
- Сервисы (бизнес-логика, кэширование, блокировки, маппер)
- Многопоточность (параллельные вызовы с `CompletableFuture`)

### Тесты с Kafka 3.8
В самом сервисе Kafka не используется — это REST API для учёта книг. Однако для изучения работы с Kafka была написана серия интеграционных тестов с Testcontainers по возрастанию сложности:

1. **Базовый продюсер/консюмер** — отправка и получение сообщений с нативными клиентами Kafka без Spring
2. **Повторная отправка и ручное подтверждение** — повторные попытки при сбоях с увеличивающейся задержкой, ручное подтверждение через `acknowledge(-1)`, использование `KafkaMessageListenerContainer`
3. **Идемпотентность через @KafkaListener** — защита от повторной обработки одного и того же сообщения через `ConcurrentHashMap`, Dead Letter Queue для необработанных сообщений
